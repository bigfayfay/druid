# Druid SQL Parser 性能优化方案

## 一、当前性能现状

```
TotalCalls=694,137 | ElapsedSpeed=4,958 ops/s | 运行时间=140s
OS CPU[cores=16, system=27.4%, jvm_process=12.5%]
JVM Heap: 2.0 GB (used=113.4 MB) | G1 GC
Concurrency=2.1
```

| 指标 | 当前值 | 分析 |
|------|--------|------|
| CPU 利用率 | 12.5%（≈2核/16核） | **严重浪费，87% 空闲** |
| 并发度 | 2.1 | 远低于可用核心数 |
| 吞吐量 | ~5,000 ops/s | 与 CPU 利用率匹配，非极限 |
| 71.1% SQL 解析耗时 | 400μs-1ms | Druid AST 解析固有开销 |
| 平均 SQL 长度 | 565 字符 | 中等长度 |
| Heap 使用率 | 113MB / 2GB（5.7%） | GC 不是瓶颈 |
| 失败率 | 0.01% | 解析稳定性良好 |

## 二、瓶颈定位

### 主要瓶颈：并发度不足

- 脚本默认 `PERF_THREAD_COUNT=1`，实际可能只跑了 1-2 个消费者线程
- 16 核机器只利用了 2 核，吞吐量受限于单线程解析速度
- Druid 的 `ParameterizedOutputVisitorUtils.parameterize()` 是 CPU 密集型操作，适合多线程并行

### 次要瓶颈：重复 SQL 未缓存

- 未开启 `--cache`，相同 SQL 每次都重新解析
- 审计数据中重复 SQL 比例通常较高（同一业务反复执行）

### 非瓶颈项

- ❌ GC：Heap 使用仅 113MB，G1 回收压力极小
- ❌ I/O：生产者-消费者模型已解耦 DB 读取和 CPU 解析
- ❌ 锁竞争：各线程独立解析，无共享状态

## 三、优化方案

### 方案 1：提高并发线程数（效果最大，预期 4-8x 提升）

**原理**：SQL 解析是纯 CPU 计算，线性扩展到核心数。

```bash
./run-perf.sh --threads 8 --queue-capacity 50
```

| 线程数 | 预期吞吐量 | CPU 利用率 |
|--------|-----------|-----------|
| 1（当前） | ~5,000 ops/s | 12% |
| 4 | ~18,000 ops/s | 45% |
| 8 | ~32,000 ops/s | 70% |
| 12 | ~40,000 ops/s | 85% |

> **建议值**：`threads = CPU核心数 × 0.6 ~ 0.75`，即 16核机器用 10-12 线程，留余量给 GC、生产者和系统。

### 方案 2：开启 SQL 模板缓存（对重复 SQL 效果显著）

**原理**：`AkLightweightCachedOutputVisitorUtils` 基于 LRU 缓存已解析结果，命中缓存直接返回 MD5+模板。

```bash
./run-perf.sh --threads 8 --cache
```

| 重复率 | 缓存收益 |
|--------|---------|
| < 10% | 提升不明显 |
| 30-50% | 提升 30-50% |
| > 70% | 提升 2-3x |

> 审计数据通常重复率较高（相同业务 SQL），建议开启。

### 方案 3：JVM 参数调优（预期 10-20% 提升）

#### 3.1 推荐 JVM 参数（G1 GC，适合大多数场景）

```bash
--jvm '-Xms2g -Xmx2g -XX:+UseG1GC -XX:MaxGCPauseMillis=50 -XX:+ParallelRefProcEnabled -XX:+AlwaysPreTouch -XX:-TieredCompilation -XX:+UseCompressedOops'
```

| 参数 | 作用 | 说明 |
|------|------|------|
| `-Xms2g -Xmx2g` | 固定堆大小 | 避免运行时堆扩容触发 Full GC |
| `-XX:MaxGCPauseMillis=50` | G1 暂停目标 50ms | 减少长停顿影响吞吐 |
| `-XX:+ParallelRefProcEnabled` | 并行引用处理 | 加速 GC 引用清理阶段 |
| `-XX:+AlwaysPreTouch` | 启动时预分配物理内存 | 避免运行时缺页中断 |
| `-XX:-TieredCompilation` | 跳过 C1 直接 C2 编译 | 热路径更快（适合长跑批处理） |
| `-XX:+UseCompressedOops` | 压缩指针 | 减少对象头开销（< 32GB heap 自动开启） |

#### 3.2 纯吞吐量场景（Parallel GC）

如果不关心延迟，只追求最大吞吐量：

```bash
--jvm '-Xms2g -Xmx2g -XX:+UseParallelGC -XX:ParallelGCThreads=4 -XX:+AlwaysPreTouch -XX:-TieredCompilation'
```

> Parallel GC 比 G1 吞吐量高 5-10%，但 STW 暂停更长。批处理场景适合。

#### 3.3 JDK 17+（ZGC 超低延迟）

```bash
--jvm '-Xms2g -Xmx2g -XX:+UseZGC -XX:+AlwaysPreTouch -XX:-TieredCompilation'
```

### 方案 4：队列参数调优

```bash
--queue-capacity 50 --batch-size 2000
```

| 参数 | 当前值 | 建议值 | 说明 |
|------|--------|--------|------|
| `queue-capacity` | 20 | 50 | 增大缓冲区，减少生产者阻塞 |
| `batch-size` | 1000 | 2000 | 增大批次，减少 DB 查询次数 |

## 四、综合推荐命令

### 高性能推荐配置

```bash
./run-perf.sh \
    --threads 10 \
    --cache \
    --queue-capacity 50 \
    --batch-size 2000 \
    --jvm '-Xms2g -Xmx2g -XX:+UseG1GC -XX:MaxGCPauseMillis=50 -XX:+ParallelRefProcEnabled -XX:+AlwaysPreTouch -XX:-TieredCompilation'
```

### 预期效果

| 优化项 | 单独提升 | 组合后 |
|--------|---------|--------|
| `--threads 10` | 4-6x | - |
| `--cache` | 1.5-3x（取决于重复率） | - |
| JVM 调优 | 10-20% | - |
| 队列+批次 | 5-10%（减少等待） | - |
| **组合总计** | - | **预期 20,000-40,000 ops/s** |

## 五、代码级优化建议（进阶）

如果上述配置优化仍不满足需求，可考虑代码级改动：

### 5.1 减少对象分配（热路径 GC 压力）

当前每次解析都创建 `new ArrayList<Object>()`，可复用 ThreadLocal：

```java
private static final ThreadLocal<ArrayList<Object>> PARAM_LIST = 
    ThreadLocal.withInitial(() -> new ArrayList<>(32));

// 使用前 clear，避免每次 new
ArrayList<Object> params = PARAM_LIST.get();
params.clear();
```

### 5.2 避免重复 String 分配

`AkTemplateResult` 每次都 new 一个新对象，可考虑对象池或结构体复用。

### 5.3 关闭监控开销

如果不需要实时监控，`--no-monitor` 可省去 `AkSqlTemplateMonitor` 的计时和统计开销：

```bash
./run-perf.sh --threads 10 --cache --no-monitor
```

### 5.4 批量 MD5 计算

当前每条 SQL 单独算 MD5，可考虑批量场景下使用 `MessageDigest` 复用（避免每次 `getInstance`）。

## 六、性能验证方法

优化后用以下方式验证效果：

```bash
# 1. 短跑验证（10万条快速对比）
./run-perf.sh --threads 10 --cache --max-records 100000

# 2. 观察关键指标
# - ElapsedSpeed 应 > 20,000 ops/s
# - CPU jvm_process 应 > 60%
# - Concurrency 应接近线程数
# - GC pause < 100ms
```

## 七、总结

当前的核心瓶颈是**并发度严重不足**（16核只用了2核），不是 JVM 或 GC 问题。

**优先级排序：**
1. 🔴 `--threads 8~12`（最重要，立竿见影）
2. 🟠 `--cache`（开启缓存，减少重复解析）
3. 🟡 JVM 参数优化（固定堆 + 编译优化）
4. 🟢 代码级优化（对象复用、监控开关）
