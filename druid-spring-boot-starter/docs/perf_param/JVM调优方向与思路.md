## 一、对现有思路的几个质疑

开始分析之前，先把我对现有方案的不同判断摆出来。

### 1.1 "K=15" 的分配膨胀系数不可靠

现有方案从监控数据回算 K，然后保守取 15，用来估算 Eden 大小。但我看出了问题：

```
node203：heap used = 1.4GB，Eden used = 860MB
但 heap used 包括 Eden 正在使用的 860MB，这些是还没 GC 的临时对象
如果上一个 Young GC 刚结束，heap used 会瞬间降到只有 Old Gen 的 562MB
```

现有方案假设 Eden committed ≈ Eden 在 GC 间隔内的最大填充量。但在 G1 下，Eden 大小是**动态调整**的——G1 根据暂停目标实时调整 Eden 区域数量，Eden committed 不代表"填满了这么多"。

**我的判断**：K 的真实值应该在 **6~12** 之间，取 15 太保守，高估了 25%~150% 的实际分配速率。这意味着现有方案估算的堆大小**偏大**。

### 1.2 "Old Gen = 200 + N×80" 公式缺少一个维度

这个公式只用了数据量（亿）一个变量来拟合 Old Gen，但 5 亿数据的 4 个节点 Old Gen 从 267MB 到 664MB 分布，跨度 2.5 倍。

| 节点 | 数据量 | Old Gen | avgLen | NonSupport | 模板重复率（推测） |
|------|--------|---------|--------|------------|-----------------|
| node160 | 5亿 | **267 MB** | 512 B | 0.22% | 高（大量重复 SQL） |
| node116 | 5亿 | 432 MB | 778 B | 49% | 中 |
| node107 | 5亿 | 465 MB | 4579 B | 68% | 低 |
| node203 | 5亿 | 562 MB | 405 B | 0.17% | 中 |
| node135 | 5亿 | **664 MB** | 198 B | 0% | **低**（模板多样） |

**看清了吗？** avgLen 最短的 node135 反而 Old Gen 最大——因为短 SQL 的模板种类更多（不同表、不同条件），LRU 缓存条目更多。而 avgLen 最长的 node160 Old Gen 最小——长 SQL 反而是重复的固定语句。

**Old Gen 的主要决定因素是模板种类数，不是数据量。** 公式拟合数据量和 Old Gen 的关系是"假相关"——只是因为数据量越大的节点运行时间越长，暴露的模板种类越多。这个因果关系弄反了。

**影响**：如果某个新部署的 SQL 模板高度重复（比如只审计同一张表的操作），旧公式会严重高估 Old Gen；反之如果模板极其分散，旧公式可能低估。

### 1.3 M 档和 L 档的区分可能没有意义

现有方案的四档：

| 档位 | OS 内存 | 线程 | Xmx |
|------|---------|------|-----|
| S | 8GB | 1 | 1G |
| M | 16GB | 4 | 2G |
| L | 32GB | 4 | 4G |
| XL | 64-128GB | 10 | 6G |

M 和 L 都是 **4 线程**。线程数相同意味着：
- 分配速率相同（同样处理 SQL/s）
- Young GC 需求相同
- Eden 大小需求相同

**Xmx 差一倍的理由只有一条**：L 档的节点处理的数据量更大，Old Gen 可能更大。但问题是：
1. Old Gen 一旦 LRU 缓存占满就会收敛，不是无限增长
2. 对于 G1，堆越大单次 GC 暂停时间越长（需要扫描更多 region）
3. 给一个 4 线程场景分配 4GB 堆，G1 的暂停反而可能比 2GB 堆更差

**我的判断**：M 和 L 应该使用相同的 Xmx（2GB 或 3GB），而不是一个 2G 一个 4G。"OS 内存有富余就给堆喂大"是批处理的思路，在低延迟场景下适得其反。

### 1.4 "XL 档 G1 也能做到 50ms 暂停"可能不成立

10 线程、11,600 SQL/s、avgLen=500、K≈10：
```
AR = 11,600 × 500 × 10 = 58,000,000 B/s ≈ 55 MB/s
```

要在 50ms 暂停目标下处理 55 MB/s 的分配：
- G1 需要将 Eden 控制得很小（~300-500MB？）
- 导致 Young GC 每 5~10 秒一次
- 并发标记周期还没跑完，新的 Mixed GC 又触发了
- GC CPU 开销可能到 10~15%

现有方案说 GC CPU 影响 ~3%，这是基于 4 线程 2GB 堆的数据。**10 线程的场景完全不同**。G1 在 10 线程高分配率下能否稳定保持 50ms 暂停，是个没有验证过的假设。

## 二、从第一性原理重新分析

### 2.1 这个 workload 的内存行为到底是什么

抛开所有公式和估算，Druid SQL 解析的内存行为只有一个特征：

> **分配快，死亡更快。**

```
一条 SQL 的生命周期：
SQL 文本进入 → 词法分析 → LALR 解析 → AST 构建 → 模板提取 → 对象全部不可达
               ├── 全部在这个时间窗口内完成 ──┤
               └──────── 0.1~0.8ms ──────────┘
```

这意味着：
- 99.9% 的对象**活不过 1ms**
- 没有"中年"对象（不会在 Survivor 区来回拷贝最终进入 Old Gen）
- Old Gen 的增长只来自 LRU 模板缓存和少量框架对象
- Metaspace 在启动后就不变了

这个模式跟 Web 应用（Session → Request → Response，对象生命周期几百毫秒到几秒）完全不同。它更像一个 **流处理应用**：数据流经管道，处理完就丢弃。

**对 GC 的含义**：
- 每次 Young GC 可以回收 99%+ 的 Eden 空间（几乎没有 survivors 晋升）
- Old Gen 增长极为缓慢（只在发现新模板时）
- G1 的 concurrent marking 大部分时间在"确认 Old Gen 没什么要回收的"

### 2.2 真正的瓶颈在哪里

看监控数据（4 线程场景）：

| 节点 | ExecSpeed | CPU% | 主频？ | 
|------|-----------|------|--------|
| node62 | 1,946 ops/s | 25.1% | 16核 |
| node203 | 1,811 ops/s | 25.2% | 16核 |
| node135 | 1,967 ops/s | 25.5% | 16核 |
| node160 | 1,961 ops/s | 25.6% | 16核 |

4 个正常节点高度一致：
- ExecSpeed ≈ **1,900~1,960 ops/s**
- CPU% ≈ **25%**（4 线程 / 16 核 = 25%）

**这不是巧合。** 4 线程处理 ~1,900 SQL/s 说明单线程吞吐约 **475~500 SQL/s**。CPU 用了 4/16 核，恰好是 25%。

**结论**：当前吞吐量的瓶颈不在 GC，也不在内存，而在**单线程的 SQL 解析速度**。Druid Parser 的处理能力大约是 **500 SQL/s/线程**。要提升吞吐量：
- 要么升级 CPU 单核性能
- 要么增加线程数
- 要么优化 Parser 本身（非 JVM 参数范围）
- **JVM 参数调优不会显著提升吞吐量**

### 2.3 CPU 和 GC 的关系要重新梳理

现有文档说"GC CPU 占比约 2-3%"，但这个数字对调优决策没有指导意义。因为：

```
GC 对实时审计的影响不是 CPU，而是 STW 暂停

关键问题是：
  50ms 的 STW 暂停 = 50ms 没有任何 SQL 被审计
  
在 50ms 内：
  1 线程场景 ≈ 25 条 SQL 未经审计就过去了
  4 线程场景 ≈ 100 条 SQL
  10 线程场景 ≈ 250 条 SQL
```

所以**暂停时间绝对值**才是关键，不是 GC 占了多少 CPU。

### 2.4 线程数 × 暂停时间 = 审计延迟的精确公式

```
审计延迟（最坏情况）= GC STW 暂停时间 + 业务排队时间

业务排队时间取决于：
  - 数据到达速率 R（SQL/s）
  - 处理速率 P（SQL/s，取决于线程数 × 单线程吞吐）
  - 队列长度

当 R < P 时：排队时间 ≈ 0，审计延迟 ≈ GC STW 暂停
当 R > P 时：队列不断增长，审计延迟无限增长
```

**关键判断**：从数据看，当前 R（~1,900）≈ P（~500 × 4），处于临界状态。这说明：
1. GC 暂停是导致审计延迟的主要因素
2. 如果 GC 暂停 50ms，所有线程同时停顿，审计延迟增加 50ms
3. 恢复后队列追平，延迟恢复正常
4. **偶发的 50ms 延迟对于实时审计可能是可接受的，但累积的 GC 暂停超过一定比例就会有问题**

## 三、我的建议

### 3.1 GC 选型：从"看 JDK 版本"改为"看线程数"

现有方案：
```
JDK 8 → G1
JDK 17+ → XL 档用 ZGC，其他用 G1
```

我的建议：

```
1 线程（S 档） → G1，MaxGCPauseMillis=100（不是 50）
                 理由：1 线程暂停 50ms 和 100ms 对审计的影响可接受
                       GC 太频繁反而降低原本就很紧张的单线程吞吐

4 线程（M/L 档）→ G1，MaxGCPauseMillis=50
                 理由：4 线程场景经过验证，暂停 20-40ms 可实现

10 线程（XL 档）→ ZGC（JDK 17+）或 G1 + MaxGCPauseMillis=100（JDK 8）
                 理由：G1 在 10 线程高分配率下稳定跑 50ms 暂停存疑
                       如果只能用 JDK 8，放宽到 100ms 比强行压 50ms 更稳
```

**S 档把 MaxGCPauseMillis 设为 100 而不是 50 的原因**：
- 1 线程场景下，吞吐比暂停更重要
- SQL/s 只有 ~2,000，50ms 暂停只影响 ~100 条 SQL
- 频繁 GC 降低单线程吞吐，这个代价在 1 线程场景下更显著

### 3.2 不要过度依赖公式估算，优先走"部署后校准"的路线

现有方案的核心是给出精确的内存估算公式，让用户"算出来"需要多少堆。这不现实：
- K 值不确定（6~12 波动）
- Old Gen 取决于模板种类（部署前无法预知）
- 实际分配率取决于 SQL 复杂度（跟 avgLen 不线性相关）

**更好的方法**：

```
首次部署（Day 0）：
  - 用保守的堆大小（比合理的略大）
  - Xmx 不设上限（OS 允许范围内）
  - 一定开启 GC 日志

数据采集（Day 1-3）：
  - 看 GC 日志中 Old Gen 的稳定值
  - 看 Young GC 频率和暂停时间
  - 看是否有 Full GC

精准调整（Day 3）：
  - 根据 Old Gen 实测值缩/扩堆
  - 根据暂停时间调整 MaxGCPauseMillis
  - 根据 GC 频率调整 G1MaxNewSizePercent
```

不要在 Day 0 追求"精准参数"——这是不可能做到的。**Day 3 的一次调整，效果好过 Day 0 的十轮公式推算**。

### 3.3 简化分档

我的建议：**三档就够了**。

```
档位 A（原 S）：8GB OS / 1 线程 / Xmx=1G / G1 / MaxGCPauseMillis=100
档位 B（原 M+L）：16-32GB OS / 4 线程 / Xmx=2G / G1 / MaxGCPauseMillis=50
档位 C（原 XL）：64-128GB OS / 10 线程 / Xmx=4-6G / ZGC（JDK 17+）或 G1（JDK 8）
```

理由：
- 4 线程场景下 2GB 和 4GB 的差异对 GC 行为影响很小
- 合并 M 和 L 可以减少 50% 的维护工作量
- 唯一需要区分 M 和 L 的情况：如果 L 档处理的数据量大到 Old Gen 超 1.5GB，才单独处理

### 3.4 关键参数的原则——不因小失大

```
一定要调的：
  MaxGCPauseMillis     → 50（4线程）或 100（1线程/10线程JDK8）
  Xms=Xmx              → 固定堆（C 调用场景必须）
  ExitOnOutOfMemoryError → true（C 侧需要感知 JVM 状态）
  GC 日志              → 必须开启（否则无法做二次调整）

可以调的（但收益有限）：
  G1HeapRegionSize     → 堆/2048 附近选一个值
  G1NewSizePercent     → 10-15%，设一个保证 Eden 最小的值
  G1MaxNewSizePercent  → 20-30%，设一个保护性上限防止 Eden 膨胀
  InitiatingHeapOccupancyPercent → 35，提前标记防 Full GC
  ConcGCThreads        → 1-2（保守，别跟业务线程抢 CPU）

不需要调的（现有方案过度设计了）：
  ParallelGCThreads    → G1 自动选，手动设可能不优
  UseStringDeduplication → 实测收益 15-30%，可以开，但别指望靠这个省堆
  AlwaysPreTouch       → 8GB 场景慎用（物理内存不足时导致启动失败）
  UseAdaptiveSizePolicy → G1 默认就是 adaptive，显式设没有意义
```

### 3.5 一个被忽略的问题：C 调用 JAR 的启动参数传递

现有方案给出的都是 `java -X... -jar` 形式的命令。但真实场景是 C 程序调用 jar：

```c
// C 侧可能的调用方式（推测）
system("java -Xms1g -Xmx1g -jar druid-ak.jar");
// 或
execvp("java", args);  // args 中包含 JVM 参数
```

这意味着：
- C 代码中硬编码的 JVM 参数修改需要重新编译 C 程序
- 更好的方式：C 侧读取一个外部配置文件，或通过环境变量传递

**建议**：明确 JVM 参数的传递方式（外部配置/环境变量），否则再好的参数也落不了地。

## 四、一个更简单的思考框架

抛开所有细节，这个场景的 JVM 调优本质上是三个参数的权衡：

```
Xmx（堆大小） ←→ MaxGCPauseMillis（暂停目标） ←→ GC 频率

三个参数只能同时满足两个：
- 堆小 + 暂停短 → GC 非常频繁（S 档的困境）
- 堆大 + 暂停短 → GC 频率适中，但 G1 暂停时间随堆增大（G1 的局限）
- 堆小 + 低频率 → 暂停长（不可接受）
```

**正确的解决路径**：

对于 4 线程以下场景 → G1，找到暂停和堆的平衡点（已验证 2GB/50ms 可行）

对于 10 线程场景 → 换 ZGC，摆脱三个参数之间的约束。ZGC 的暂停时间**与堆大小无关**，大堆 + 短暂停可以同时实现。

**所以真正的决策树只有两问**：

```
Q1: 几个线程？
  └── 1-4 线程 → G1
  └── 10 线程 → 能不能升级 JDK 17+ 用 ZGC？
                  ├── 能 → ZGC，选择结束
                  └── 不能 → G1，但要接受暂停可能超过 50ms

Q2: 能不能 Day 1 看 GC 日志？
  └── 能 → 初始参数不要太纠结，Day 3 校准
  └── 不能 → 先用保守值，留余量
```

## 五、与现有方案的关键差异汇总

| 维度 | 现有方案 | 我的判断 | 差异原因 |
|------|---------|---------|---------|
| K 值 | 15 | 6~12，取 15 太高 | 现有方案使用 Eden committed 而非实际填充量推算 |
| Old Gen 公式 | 200 + N×80 | **模板种类数才是主因**，这个公式不可靠 | 5 亿数据的 4 个节点 Old Gen 分布 267~664MB，覆盖不了 |
| M/L 档区分 | 独立两套参数 | **合并**，唯一区分是数据量大时 Xmx 略大 | 线程数相同→Eden 需求相同 |
| XL 档 G1 暂停 | 可达 50ms | 高分配率下存疑，JDK 8 应放宽到 100ms | 没有 10 线程场景实测数据支撑 |
| S 档暂停目标 | 50ms | 放宽到 100ms | 1 线程吞吐更重要，50ms/100ms 差异不大 |
| 参数精确度 | 追求 Day 0 精确公式 | Day 3 校准比公式更重要 | 缺少 GC 日志等关键输入，公式无法精准 |
| AlwaysPreTouch | 全部开启 | 8GB 场景慎用 | 物理内存不足风险 |
| 分档数量 | 4 档 | 3 档（M/L 合并） | 维护成本降低 50%，GC 行为无差异 |
