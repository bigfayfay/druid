## 二、CPU 消耗预估

### 基准数据（来自压测结果）

| 场景 | 单次耗时 | 吞吐量 |
|------|---------|--------|
| **无缓存**（Druid 完整解析） | ~1,434 µs | ~697 ops/s/核 |
| **缓存命中**（LRU 对照提取） | ~426 µs | ~2,345 ops/s/核 |

### 按日总量推算 CPU 需求

```
无缓存方案:
  909M × 1,434 µs = 1,303,506 CPU-秒/天 ≈ 15.1 CPU-核 × 24h

缓存命中方案:
  909M × 426 µs = 387,234 CPU-秒/天 ≈ 4.5 CPU-核 × 24h
```

### 14 进程分配

| 场景 | CPU 总需求 | 每进程平均 | 说明 |
|------|-----------|-----------|------|
| 无缓存 | ~15 核 | ~1.1 核/进程 | 如果全部是 SQL 解析，CPU 应饱和 |
| 缓存命中 | ~4.5 核 | ~0.3 核/进程 | 缓存有效时 CPU 压力小 |
| 混合（~50% 命中） | ~8.5 核 | ~0.6 核/进程 | 更接近真实场景 |

**如果 CPU 占用高**，可能原因：
1. **缓存未部署** → 还在走 `CustomerOutputVisitorUtils` 无缓存路径
2. **缓存命中率低** → SQL 模板多样性高，LRU 1000 条不够，频繁驱逐
3. **C# 调用层开销** → SSH/进程间通信本身消耗 CPU
4. **非 SQL 解析的其他业务逻辑** → 14 个进程不全是 Druid 解析

## 三、需要收集的数据

### 首批关键数据（一次采集即可）

```bash
# 收集日期
date=$(date +%Y%m%d%H%M)
outdir="/tmp/druid_diag_$date"
mkdir -p "$outdir"

# 1. 所有 Java 进程清单
ps aux | grep -i '[j]ava' > "$outdir/java_processes.txt"

# 2. 各进程 CPU/内存
top -b -n 1 > "$outdir/top_output.txt"

# 3. JVM 版本 + 参数
java -version 2>&1 > "$outdir/java_version.txt"
for pid in $(pgrep -f '[j]ava'); do
    jcmd $pid VM.flags > "$outdir/jvm_flags_$pid.txt" 2>&1 || true
done

# 4. GC 日志位置（如果有 -Xloggc 参数）
ps aux | grep -i '[j]ava' | grep -o '\-Xloggc:\S\+' > "$outdir/gc_log_paths.txt" 2>&1

# 5. 系统资源概况
echo "--- CPU info ---" > "$outdir/system_info.txt"
cat /proc/cpuinfo | grep 'model name' | head -1 >> "$outdir/system_info.txt"
grep -c '^processor' /proc/cpuinfo >> "$outdir/system_info.txt"
echo "--- Load ---" >> "$outdir/system_info.txt"
cat /proc/loadavg >> "$outdir/system_info.txt"
echo "--- Memory ---" >> "$outdir/system_info.txt"
free -m >> "$outdir/system_info.txt"
echo "--- Disk ---" >> "$outdir/system_info.txt"
df -h / >> "$outdir/system_info.txt"
echo "--- ulimit ---" >> "$outdir/system_info.txt"
ulimit -a >> "$outdir/system_info.txt"

echo "Done: $outdir"
```

### 持续监控建议

| 维度 | 工具/方法 | 采样间隔 |
|------|----------|---------|
| 进程级 CPU | `druid_monitor.sh`（已附） | 60s |
| GC 活动 | `jstat -gcutil <pid> 60s` | 60s |
| 缓存命中率 | `DruidSqlMonitor.printAll()` | 按需调用 |
| SQL 吞吐量 | 应用层埋点日志 | 实时 |

## 六、回答你的核心问题

> 每秒需要处理多少数据量

**~10,500 QPS**（日均），峰值可能更高。每个 CPU 核在无缓存时只能处理 ~700 QPS，需要 ~15 核才能扛住。如果 14 个进程中有大多数参与 SQL 解析，CPU 高是正常的。

> CPU 使用情况

**如果未启用缓存**：14 个进程贴满 CPU 是合理预期。压测数据表明一核约 700 QPS，10,500 QPS 需要约 15 个满核。

**如果已启用缓存**：缓存命中场景一核约 2,345 QPS，10,500 QPS 只需约 4.5 核。CPU 仍高的话说明命中率低或有其他业务消耗。

> 需要你提供什么数据

上面的**首批关键数据**（`/tmp/druid_diag_*/`）一次采集即可。特别是：
1. `java_processes.txt` — 确认哪些进程是 Druid 解析
2. `jvm_flags_*.txt` — 确认 GC 参数和堆大小
3. `gc_log_paths.txt` — 找到 GC 日志分析 GC 开销
4. 缓存命中率 — 确认当前是否已启用 LRU 缓存
